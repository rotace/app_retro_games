# Research: Debian環境でのパーリンノイズ描画機能

## Decision: Framebufferアクセス方法

*   **決定**: Linux Framebuffer (`/dev/fb0`) への直接メモリーマップドI/O (mmap) を使用する。
*   **理由**:
    *   古いDebian環境（CUIのみ）での描画要件を満たす。
    *   外部依存を最小限に抑え、軽量性を追求する。
    *   OSのグラフィックスレイヤーを介さないため、パフォーマンスが高い。
    *   プロジェクトの憲法「Linux Framebuffer (`/dev/fb0`)への直接ピクセル単位書き込み」に準拠する。
*   **代替案**:
    *   **SDL/Allegroなどのグラフィックスライブラリ**: 軽量性、依存関係の最小化という制約に反するため不採用。古いDebian環境でこれらのライブラリをセットアップする複雑さも考慮。
    *   **X Window Systemの利用**: CUIのみの環境がターゲットであるため不採用。

## Decision: パーリンノイズ生成の統合

*   **決定**: `core` クレートで `noise` クレートを使用してパーリンノイズを生成し、生のピクセルデータを `runner-debian` に渡すインターフェースを定義する。
*   **理由**:
    *   プロジェクトの憲法「厳格な依存方向: `ランナー層 ➔ コア層`」に準拠し、コア層の独立性を保つ。
    *   「データ駆動型インターフェース」の原則に従い、描画ロジックとノイズ生成ロジックを分離する。
    *   ランナーは描画に特化し、コアはデータ生成に特化するという役割分担が明確になる。
*   **代替案**:
    *   **`runner-debian` でノイズを生成**: コア層の独立性を損ない、描画ロジックがプラットフォーム層に漏れ出すため不採用。
    *   **`core` が直接描画インターフェースを持つ**: コア層が外部の具象（OS、画面描画ライブラリ）に依存することになり、憲法に違反するため不採用。

## Decision: `unsafe` コードの取り扱い

*   **決定**: Framebufferへの直接アクセスには `unsafe` ブロックを使用するが、その使用は `runner-debian` クレート内の `framebuffer.rs` のような専用モジュールに限定し、安全性の根拠（`// SAFETY:` コメント）を詳細に記述する。
*   **理由**:
    *   プロジェクトの憲法「`unsafe` コードの制限」に従い、必要不可欠な場合にのみ使用し、その範囲と安全性を明確にする。
    *   メモリ安全性への影響を最小限に抑え、コードレビューを容易にする。
*   **代替案**:
    *   **`unsafe` コードの使用を完全に避ける**: Framebufferへの直接アクセスはRustの安全な抽象化では困難であり、事実上実現不可能であるため不採用。
    *   **`unsafe` コードを広範囲に使用する**: コードの安全性を損ない、デバッグを困難にするため不採用。

## Decision: エラーハンドリング

*   **決定**: Framebufferのオープン、mmap、ioctlの呼び出しなど、すべてのシステムコールは `Result` 型でエラーを適切に処理し、上位層に伝播させる。
*   **理由**:
    *   プロジェクトの憲法「パニック禁止」に準拠する。
    *   ランタイムエラーが発生した場合でも、アプリケーションがクラッシュすることなく、適切なエラーメッセージをユーザーに提供できるようにする。
*   **代替案**:
    *   **`unwrap()` や `expect()` を使用**: アプリケーションがクラッシュする可能性があり、憲法に違反するため不採用。

## Decision: WSLg環境でのシミュレーション

*   **決定**: WSLg環境では、`runner-debian` がLinux Framebufferを適切にエミュレートするか、あるいは別途X11またはWayland経由でウィンドウ描画を行うための代替実装を検討する。初期段階では、FramebufferアクセスがWSLgでそのまま機能することを期待し、もし問題があれば代替実装を研究する。
*   **理由**:
    *   開発目標としてWindows環境（WSLg）での完全シミュレーションが掲げられているため、これを達成する必要がある。
*   **代替案**:
    *   **WSLgでのシミュレーションを完全に省略**: 開発目標に違反するため不採用。
